# Phase 3 — Package Drafts and Administrator Price Previews

Historical implementation record: Phase 3.5 supersedes this document wherever it assumes five seeded commercial families, a fresh Food Pack minimum of 10, mandatory rice/drink/dish groups, mandatory lechon kilograms/trays, or behavior selected by a historical family code. Fresh installations have no commercial collections; Administrators create collections and configure required Selection Groups. See [Phase 3.5](10-phase-3-5-dynamic-collections.md) for current rules. Names and prices below are examples, not production defaults.

Implemented 2026-10-09. This phase creates editable, administrator-only package configurations for Main Catering, Belly Lechon, Food Pack Lunch and Pica-Pica. Food Tray Menu still requires its separate direct-listing implementation. No package draft is published, customer-bookable, or a commercial quotation.

## Entities and migration decisions

`2026_10_09_000005_create_package_drafts.php` adds `products` → `product_variants` → `variant_versions` → `selection_groups` → `group_options`, plus `group_category_rules` and `group_dish_rules`. All child FKs restrict deletion; the draft slot removal Action explicitly removes children in one transaction. PostgreSQL checks constrain codes, modes, nonnegative BIGINT centavos, count ranges, quantity overrides, PHP currency and draft-only status. Triggers reject Food Tray package variants, cross-family versions/options, wrong family pricing units or slot types, invalid lechon/tray serving units and Pica-Pica premiums. The canonical `dishes` and Phase 2 offering/eligibility tables remain the only dish masters.

`selection_groups.slot_kind` explicitly distinguishes rice, drink, dish, lechon, tray and bundle-item slots. This is a Phase 3 addition to the earlier logical ERD so the family-specific workflow can be validated without inferring semantics from arbitrary group names. `group_options` carries nullable snapshot columns reserved for Phase 4; Phase 3 never claims they are populated or immutable. `variant_versions` has a draft revision for stale form edits. Phase 4 must implement published states, current-version pointers, immutable snapshots, publication validation, cloned revisions and concurrent publication handling before any customer use. The Phase 3 database check intentionally forbids `published` status until that migration.

Food Pack's family minimum is **10 packs**, as explicitly approved in the Phase 3 instructions, replacing Phase 2's neutral one-pack seed. Fresh installations seed 10. The migration updates only an unchanged neutral Phase 2 default (minimum 1, step 1, no maximum, no floor, unchanged timestamp); an administrator-edited default is preserved. Main Catering retains its enforced 150-pax floor. Other family defaults remain one set; variants may inherit or override within the family rules. Only demo tests use illustrative prices; no example commercial rates are seeded.

## Workflow and validation

Package administration uses `PackagePolicy`, `SaveProduct`, `SaveVariantDraft`, `SaveSelectionGroup` and `DeleteSelectionGroup`. `package.view` permits draft viewing/preview; `package.manage` permits product and slot editing; `package.pricing.manage` is additionally required for variant base-price editing and nonzero option premium changes. Admin receives all capabilities through the existing resolver; Staff starts without package grants. Form Requests and Actions both enforce relevant authorization. Product, version and slot changes are audited in the existing append-only audit table.

`PackageQuantityRules` resolves family defaults and nullable variant overrides, and fails closed when defaults are missing. `PackageSelectionValidator` validates every allocation against the same version's groups, option allow-list, current Phase 2 availability, category quotas, dish allow/deny rules, fixed inclusions and distinct canonical dishes. Identical Food Pack split selections merge before any future subgroup restrictions. Total quantity, not each subgroup, receives family/variant minimum and step checks by default. `PackagePricePreview` computes exact integer-centavo base and option adjustments per pax, pack or set; it checks overflow and returns decimal strings with a structured group breakdown. Client-provided price fields are ignored. Preview is not persisted.

Draft displays and previews resolve inherited ordering defaults live. Materialized effective columns on a draft are the last saved values and may lag after a family-default edit; they are **not** used as authoritative preview rules. Phase 4 publication must re-resolve and freeze the effective values in its transaction.

Family-specific constraints are explicit: Main and Food Pack need fixed rice, one required drink and customizable dish slots; Belly needs fixed or select-one kilogram options and select-many trays; Pica-Pica uses fixed bundle-item slots with no premiums. The Admin chooses actual variant labels, allowed options, selection counts, included quantities and prices. The `inclusion_count` field is per selected option per purchased unit; offering-option quantity/unit specifies its serving form. Serving capacity remains descriptive, never a kilogram-to-pax conversion or ordering rule. The preview requires all mandatory slot kinds but does not impose one hardcoded A–D configuration.

The React feature lives in `resources/js/features/packages` with small page wrappers under `resources/js/pages/admin/packages`. The builder edits relational fields through ordinary controls, not JSON. Existing configured options that become inactive appear as unavailable and can be removed; they cannot be used in a preview. A draft-only warning appears on the version page.

## Final presentation and identity clarification

`2026_10_10_000006_add_catalog_presentation_fields.php` adds family descriptions/order, product order and variant descriptions/order. It also enforces nonblank/unique normalized family display names and unique normalized variant display names per product, and guards immutable family `code`/`is_addon` in PostgreSQL. The seed supplies default order only for newly created families; existing edited presentation is preserved. `family.view` and `family.manage` are separately delegable Staff capabilities; Staff remains unprivileged by default. Family changes use a Policy, Form Request, transactional Action and audit event. Protected family ordering floors remain Admin-only.

Customer-facing family and variant labels are not identifiers. Renaming Food Pack Lunch to Packed Meals leaves `food_pack` quantity units, eligibility, selection mode and per-pack pricing intact. Messages use the current family/slot/category display name and resolved quantity/count rules. Stable family codes still select approved family-specific business behavior. Admins may create additional variants beyond A-D and independently configure their groups, options, category rules, premiums and quantity overrides. The fifth Main variant requires no source change. Food Tray remains a separate direct-listing family, not a package-variant engine.

For the future reservation workflow, one Main Catering (`main_catering`, `is_addon=false`) package will be required as the primary product. Belly Lechon, Food Pack, Food Tray and Pica-Pica are optional add-ons to that reservation. No reservation, inquiry, quotation, payment or checkout data is created by Phase 3; publication and immutable commercial snapshots remain Phase 4 work.

## Accepted Phase 3 boundaries and Phase 4 work

- No published/current version pointer, customer-facing catalog, direct tray listing, reservation, quotation or payment endpoint exists.
- Draft option/group edits do not currently advance the version's revision number; the draft revision protects the variant edit form. Phase 4 must make the revision cover the complete publishable configuration or compare a configuration digest under locks before publishing.
- Current names, quantities, category and serving facts are read from catalog records for drafts. Phase 4 must freeze these facts and rules at publication, then combine frozen commercial facts with current availability.
- Category/slot labels are administrative configuration. The current master catalog has no strict semantic tag declaring a dish to be rice or a drink, so semantic correctness of the configured offering is an administrator responsibility; family eligibility, slot modes and lechon/tray units are enforced technically.
- Production rates, actual A–D inclusions, branded drinks and serving claims remain business configuration to approve before publication.
