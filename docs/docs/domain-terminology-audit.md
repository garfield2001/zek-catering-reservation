## Deliberate distinctions and non-renames

- One catering business/installation is **not** a Collection. One current primary Collection is allowed; add-on Collections are unbounded; zero collections on a fresh install is valid.
- Collection identity (`code`/ID), role (`is_addon`), behavior (`behavior_type`), display name (`name`), current active state and archive state are separate. Only the behavior enum selects mechanics; IDs scope eligibility.
- Food Item, Food Category, Collection Eligibility, Offering, Serving Option, and Group Allowed Option are different rows with different lifecycles.
- Product, Variant, Version, Draft state and published version (future) must not collapse. “Package” describes product-family workflows, not every collection; direct-sale listing revisions are future work.
- Inclusion Group, `slot_kind`, selection mode, fixed inclusion, Category Rule and Food Item Rule are different concepts; `slot_kind` values remain stable internal mechanics keys.
- Collection ordering default, version override, effective quantity rule, serving quantity, serving capacity, purchased quantity, and selection count measure different things.
- Base price, nonnegative price adjustment/premium, transient preview, future published direct listing price, quotation and payment are not interchangeable. Currency stays integer centavos internally.
- User account, Administrator/Staff role, permission, permission override, session, Audit Event and Activity History presentation are distinct.
- Retain applied migration filenames, existing table/column names, persistent collection/permission/action codes, and historical audit event payloads unless a later specific migration is approved. Legacy identifiers are a compatibility boundary, not evidence that the UI must use legacy words.

## Naming convention for new work

Use singular PascalCase PHP classes/types and React components; plural snake_case tables and snake_case columns; kebab-case URL segments with consistent named-route domains; camelCase TS variables/functions and domain-specific PascalCase interfaces/types; feature-aligned directories. Keep Laravel route binding and Eloquent conventions explicit when a legacy key is retained. Use one approved business-facing label per entity, and distinguish internal mechanics codes from editable display names. New validation text must use current configured names and resolved quantity, unit and selection limits. Update tests and docs with any new term. No proposed rename in this document becomes mandatory until the owner approves the map.
