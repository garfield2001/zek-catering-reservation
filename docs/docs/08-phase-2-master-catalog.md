# Phase 2 — Master catalog implementation

Status: Implemented 2026-10-09. Phase 2 is deliberately limited to master culinary data and administration. Package variants, publication, Food Tray direct listings/prices, media, reservations and other later-slice workflows are not implemented.

## Data and identity

- `dish_categories` carry stable codes, names, display order and active status. PostgreSQL generated `name_key` plus a unique index makes trimmed, case-insensitive category names unique. The HTTP request reports a friendly conflict; the index remains the concurrency backstop.
- `dishes` are canonical records with stable global codes and one primary culinary category. Names are unique, trimmed and case-insensitive **within a category**, not globally; the global code identifies a dish independently of its display name. The admin search enables duplicate review across categories.
- Exactly five fixed family codes are seeded: `main_catering`, `belly_lechon`, `food_pack`, `food_tray`, `pica_pica`. They are categories of eligibility, not packages or prices. Four are marked add-ons; no reservation link is created.
- `family_order_defaults` stores one row per family. Main Catering starts with the approved minimum of 150 and its floor enforced. The other families start at a neutral technical minimum/step of 1 with floor enforcement off. Those numbers **are not approved commercial minimums**; an Admin must configure the real rules before future publication. Maximum is nullable. Only Admin can change defaults, with audit. A deferred PostgreSQL constraint trigger rejects a transaction that leaves an existing family without its default; family/default seeding occurs in one transaction. Existing installations with a gap must repair it before the enforcement migration can apply.
- `dish_family_eligibilities` uses a composite `(dish_id, family_id)` key and active flag. Removing a family from a dish deactivates the pair instead of deleting it. A composite FK from `dish_offerings` guarantees that a preparation belongs to an existing eligibility pair, including when the pair later becomes inactive. This preserves history and avoids orphaned offerings. `CatalogAvailability` checks the full current chain: active dish, category, family and pair; active offering and option are additionally required at their respective levels. A row's own active flag alone is not a purchase-availability determination.
- `dish_offerings` represent named family-specific preparations. Multiple offerings per dish and family are distinguished by a code unique within the pair. They carry no price. `offering_options` represent serving size/unit and optional explicit serving claims. Quantity is exact `NUMERIC(12,3)`; permitted units are kg, tray, portion, piece, bottle and pack. Serving pax is nullable and positive if supplied; no pax is inferred from kg. There is no price or package selection rule on options.

## Administration and safeguards

Admin may view and manage the catalog; Staff needs `catalog.view` for read access and `catalog.manage` for changes. Management does not grant the ability to edit family ordering defaults, which are Admin-only because they can become commercial publication floors. No new permission is granted to Staff by seeding. Policies and Form Requests guard HTTP operations; Actions reauthorize under transaction before mutation. Active offerings/options require current eligibility; archival and deactivation retain rows. Scoped nested routes prevent cross-dish and cross-offering edits. PostgreSQL FKs, check constraints and unique indexes backstop application validation. Catalog edits and their append-only audits commit atomically.

The admin interface provides category and dish browse/search, create/edit/detail, eligibility controls, offerings, serving options and family defaults. React components are feature-organized under `resources/js/features/catalog`; Laravel catalog controllers remain thin, with transactional Actions, a focused eligibility service and read query classes. No generic repository layer was added.

## Migration and verification

`2026_10_09_000003_create_master_catalog_tables.php` creates the seven Phase 2 tables and database constraints. `2026_10_09_000004_require_family_order_defaults.php` adds deferred total-participation enforcement for family defaults. `DatabaseSeeder` adds the five family/default rows and two catalog permissions idempotently. `tests/Feature/MasterCatalogTest.php` exercises family seeding, administrative CRUD, malformed input rejection, duplicate names, exclusive/all-family eligibility and retained inactive pairs, combined availability, family-specific offerings and varied options, direct PostgreSQL constraints, Staff/Admin authorization, nested-route isolation and transactional audit rollback. Existing Phase 1 tests remain part of the regression suite. A clean PostgreSQL migration/seed and isolated rollback/reapply smoke test verify installation, not only transactional feature tests.

Commercial family minima/steps beyond Main Catering and any customer-facing serving claims require approval before their future publication. No package, listing or media implementation is implied by this slice.
