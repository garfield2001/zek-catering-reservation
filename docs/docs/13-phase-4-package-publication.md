# Phase 4 package publication and version lifecycle

Current approved refactor: [Business workspaces and package architecture](15-business-workspaces.md) supersedes conflicting historical Variant, manual primary setup, Main Catering surcharge/Serving Option, and empty-primary-installation descriptions below. The primary Catering service is automatically provisioned; add-on services remain dynamic. Catering and compatible add-ons use a shared category/food menu builder. Package quantities are independently owned, not inherited. Advanced Serving Option rules remain internal; their ordinary manual group editor is removed.

This document records the Phase 4 package-oriented architecture. It supersedes the draft-only statements in Phase 3 and the provisional publication design in the original V3 ERD where they conflict. It does **not** authorize or represent direct-sale listings, inquiries, reservations, quotations, payments or customer checkout. The physical `product_families`, `dishes`, `selection_groups` and route identifiers remain compatibility boundaries; business labels use Collection, Food Item, Selection Group, Included Items and Customer Choices.

## Hierarchy and creation

Collection → Package Product → Package Version is the implemented hierarchy. A new Package Product creates a stable generated product code and its Version 1 Draft in one transaction. Later revisions are cloned from a published Version. Codes are stable identifiers, never derived from editable names. Catalog create forms also use backend-generated Food Category, Food Item, Offering and Serving Option codes. Legacy fixture callers can provide codes to Actions; ordinary HTTP create flows strip code input and generate it server-side. PostgreSQL uniqueness and update guards make codes stable across concurrent operations and direct writes.

Browser Package Product creation supplies a UUID `creation_token`; the family-row lock and nullable unique token let an identical retry return the existing Product instead of producing a duplicate. Conflicting token reuse is rejected. Existing Products keep a null token. New records append to their applicable presentation order. Authorized Move Up/Move Down operations lock the parent/scope, exchange positions, and audit the change. If historical values tie, the affected scope is renumbered to establish a deterministic order. Presentation ordering of Products is live; it does not rewrite the Version snapshot. Selection Group ordering is Version-owned and therefore editable only in a Draft, advancing `draft_revision`.

## Drafts, versions and publication

`package_versions.status` is `draft`, `published` or `abandoned`. A partial unique index permits at most one active Draft per Package Product. `products.current_version_id` is nullable until first publication, has a composite same-owner FK, and can advance only to a higher-numbered published Version. It cannot be cleared or moved backward. A new revision copies the selected published Version's nested groups, allowed options, category/food-item rules, prices and quantity overrides into a new higher-numbered Draft. An active Draft must be resolved before another is created. Abandonment is audited and leaves the current published pointer unchanged.

Every Draft mutation through the package Actions locks the Package Product and Draft, rechecks the revision and current catalog, validates complete feasibility, resolves current Collection quantity defaults, freezes commercial terms, changes the Version status and advances the pointer in one transaction with an Audit Event. Retries of the same already-current publication return that Version. PostgreSQL triggers reject updates/deletes to published or abandoned Versions and changes to their Selection Groups and child rules/options. Rollback of a migration with historical published/abandoned Versions is deliberately refused.

`package_versions.published_snapshot` is a versioned JSONB representation of Package Product/Collection labels, Food Item and Food Category labels/descriptions, serving facts, inclusions, selection rules, quantity rules, prices and adjustments. Stable live IDs remain in the snapshot and in relational groups for effective-availability checks. The snapshot is immutable historical commercial evidence; a master catalog rename cannot change it. Direct-sale listing publication will need its own revision identity and snapshot, rather than using package endpoints.

## Selection and availability

Fixed groups have one default Serving Option. Customer-choice groups use explicit allowed options, category quotas, Food Item allow/deny rules and selection limits. There are no globally mandatory rice/drink/meat groups. The complete-feasibility service performs bounded exhaustive search across groups, not independent option counts. It enforces canonical Food Item distinctness across Customer Choices and returns a blocking error when no full solution exists or when the 100,000-state safety limit is reached. This bound is an operational limit, not a heuristic acceptance of an unproven package. Existing per-group `unique_dishes=false` only relaxes distinctness *within* that group; cross-group choices remain distinct.

Publication validity and live availability differ. Current availability combines Collection, Package Product and catalog active/archive/eligibility conditions with the same complete feasibility check. Inactive optional options drop from new choices without mutating the snapshot; an unavailable fixed inclusion or impossible remaining choice set makes the Package Product unavailable. Restoring live eligibility can recover availability automatically unless the Product is intentionally disabled/archived. Disabling retains publication and can be reversed when its parent permits. Archiving is permanent, keeps the current published pointer/history and atomically abandons applicable active Drafts. Collection archival also abandons its active package Drafts and requires package lifecycle authority when they exist.

## Money and access

The UI accepts/display Philippine pesos, including `₱250.50`; Laravel converts decimal strings exactly to nonnegative integer centavos and retains the existing minor-unit wire fields for compatibility. Draft previews remain server-calculated, transient and explicitly not quotations. `main_package`, `packed_meal`, `package` and `fixed_bundle` retain per-pax, per-pack and per-set behavior respectively; names do not select arithmetic. The three-way maximum state is: inherit Collection Default, set a numeric custom maximum, or explicitly no package-specific maximum. This is not a statement about future event-date capacity.

Predefined `package.publish`, `package.history.view` and `package.lifecycle.manage` permissions are separate from draft management and pricing. Active Administrators retain full access. Staff receives only explicit assignments; no publishing permission is seeded for Staff. Policies and Actions enforce sensitive operations server-side; Audit Events record successful publication, cloning, abandonment, availability changes and ordering. The protected last-Administrator invariant is unchanged. The first-Administrator command now returns an actionable seed instruction when the Administrator role is absent instead of throwing `ModelNotFoundException`.

## Current boundary and verification

The package-based Main Catering, package add-on, packed-meal and fixed-bundle behaviors use this lifecycle. Direct-sale collections remain identity/eligibility contexts only. No customer transaction workflow exists. The isolated PostgreSQL test database is `zek_catering_test` on the owner's installed PostgreSQL port `5432`; tests must never target the development database. Clean installation and repeated migration runs are verified in that isolated database. The clean baseline intentionally does not provide an in-place upgrade path from the unreleased legacy Variant schema; local development records require a controlled conversion/export/import or explicit reset decision. Technical implementation is not owner acceptance or commercial-production readiness.

Selection Groups are configurable inclusions, not hardcoded rice or drink requirements. Normal package food slots may be fixed, single-choice or multi-choice; the Collection and current catalog still govern valid serving units and availability. The Admin interface explains unavailable actions and missing Food Item/Serving Option prerequisites beside the action, including on keyboard and touch interfaces. Draft forms warn before browser navigation when local changes are unsaved. The primary package navigation uses business labels while preserving existing route names and URLs as compatibility boundaries.
