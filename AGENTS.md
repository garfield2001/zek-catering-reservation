# Repository working rules

## Git ownership

The repository owner stages, commits, and pushes through GitHub Desktop. Do not run `git add`, `git commit`, `git push`, amend, reset, rebase, force-push, or rewrite history. Use read-only Git commands for inspection. Preserve unrelated work and never expose credentials or secrets. After a meaningful implementation milestone, suggest a Conventional Commit subject and a useful body; leave all Git mutations to the owner.

## Code architecture

Treat `docs/` as the primary product specification, with later explicit user decisions taking precedence. Implement only the currently authorized phase. Use a modular Laravel monolith: thin controllers, Form Requests for HTTP validation, Actions for meaningful workflows, focused services for reusable rules, Policies for authorization, Eloquent relationships and dedicated queries where useful. Keep transactions and backend business rules authoritative. Avoid generic repositories, oversized controllers, duplicate validation or business logic, unnecessary interfaces, and future-phase placeholders.

Organize React/TypeScript by feature. Keep pages small and compose reusable components; introduce hooks when stateful behavior warrants them. Keep shared UI components and types focused. Validate important failure paths with PostgreSQL integration and feature tests, then run Pint, Larastan, ESLint, Prettier, TypeScript, and the production build. Report only checks actually run.

## Domain terminology and naming review

Before adding or renaming a domain concept, check the approved vocabulary against its database definition, Laravel model and relationships, policies, routes, API/Inertia props, TypeScript types, UI labels, validation messages, tests, ERD, and documentation. Use one name for one concept and preserve distinct names for different concepts; avoid synonyms introduced only for stylistic variety. Record any intentional legacy identifier or compatibility boundary. The owner approved the vocabulary with refinements in `docs/docs/domain-terminology-audit.md`; the Phase 3.5 documentation defines approved behavior, and later explicit owner decisions take precedence.

Persisted codes and behavior types are stable internal identifiers. Editable customer-facing names, descriptions, and variant labels are presentation data and must not select pricing, eligibility, authorization, or validation behavior. Prefer the current configured name and resolved quantities/units in user-facing messages. Do not rewrite applied migrations, break route/permission identifiers, or alter historical audit data for cosmetic consistency; plan coordinated, reversible changes with compatibility tests.

Canonical implemented concepts: User Account (Team Member in account-management UI), Administrator, Staff, Permission and Permission Override, Audit Event (Activity History in UI), Food Category, Food Item, Collection, Collection Role, Collection Behavior, Collection Eligibility, Offering, Serving Option, Collection Ordering Default, Package Product, Package Variant, Variant Version and Draft state, Selection Group, Group Allowed Option, Category Rule, Food Item Rule, Quantity Rule, Price Adjustment, and Draft Price Preview. Fixed groups are **Included Items** and selectable groups are **Customer Choices** in business-facing UI. Preserve the Collection → Package Product → Package Variant → Variant Version hierarchy. Existing table/FK, route, permission, collection-code, wire-key and audit identifiers are compatibility boundaries, not UI labels.

Phase 4 package Versions may be Draft, Published or Abandoned. A Published Version and its commercial snapshot are immutable; at most one active Draft and one current Published Version belong to each Variant. Restoration clones into a higher-numbered Draft and never moves the current pointer backward. Technical codes are generated in ordinary Admin create flows, display order is changed through authorized move operations, and business-facing monetary input is in Philippine pesos while Laravel stores/calculates integer centavos. Direct-sale listing publication and customer transactions remain outside this package lifecycle.

Admin and Staff actions that are unavailable must include an accessible, business-language explanation and a safe next step when one exists. Do not rely on hover-only tooltips or unexplained disabled buttons. Distinguish permission denial, missing catalog prerequisites, incomplete Drafts, Published/Abandoned Versions, loading state, disabled offerings and archived records; keep server-side authorization authoritative. Selection Group forms must use the canonical business terms Included Items, Customer Choices, Food Items and Serving Options, and must not assume rice, drinks or culinary categories are universally required.

Permission capabilities are developer-defined; Administrators assign supported predefined permissions but cannot invent or edit their technical meanings in the UI. Staff access remains least-privileged and policy-enforced. After first provisioning, ordinary account and permission operations must retain one active, fully authorized Administrator. Serialize access mutations, protect the last Administrator, require confirmation for access transfer, and keep the secure first-admin command as the only bootstrap path. Do not replace this with a parallel RBAC scheme.

## Business policy and milestone reporting

Before implementing a new milestone, separate approved business rules, routine technical decisions, unresolved business policies, and explicitly deferred features. Ask for approval when an unresolved policy materially changes business behavior; do not invent reservation, quotation, payment, cancellation, capacity, or fulfillment rules. Only implement the authorized phase.

Every future phase completion report must include a section titled `MANUAL TESTING READINESS`. Classify it as `NOT YET READY`, `LIMITED WORKFLOW TESTING`, `READY FOR MILESTONE TESTING`, or `READY FOR FULL USER ACCEPTANCE TESTING`. Distinguish technical implementation, individual workflow, integrated business workflow, and commercial-production readiness. State fully implemented and partial workflows, deferred features, blocking dependencies, the milestone for broader testing without inventing dates, testable Admin/Staff/Customer perspectives, guided steps and expected outcomes only for genuinely ready workflows, and normal current limitations. Never equate passing automated checks with owner acceptance or commercial readiness. Report checks actually run as passed, failed, skipped, or environment-blocked; do not present previous results as newly executed.
